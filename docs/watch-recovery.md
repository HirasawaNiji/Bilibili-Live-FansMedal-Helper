# 7.5.2：观看任务恢复

此版本修复观看心跳中断后误报整轮完成，以及进度不增长后缺少补救的问题。功能由 7.5.2-beta.1 转为正式版，恢复规则保持不变。

## 安装

1. 在用户脚本管理器中备份现有脚本和配置。
2. 安装 `dist/bilibili-live-tasks-helper.min.user.js`。本版沿用正式版名称和 namespace，应覆盖现有脚本并保留配置；确认管理器中只启用一份 BLTH。
3. 安装完成后，关闭所有先前打开的 B 站直播间标签页，再打开一个用于运行任务的直播间。旧版本没有本版的独占锁，不能依靠安装动作停止已注入旧页面的脚本。
4. 确认面板中的版本为 `7.5.2`，启用观看任务。本版本保留“当前打开的直播间下播后才运行观看任务”的原有规则。

正式版恢复 GitHub Latest Release 自动更新地址。由于本地 beta 的自动更新地址设为 `none`，beta 用户需手动安装一次正式版，此后可正常自动更新。

## 恢复规则

- 每轮返回真实成功心跳时长、是否完成和结束原因。6 分钟中断不会再显示已完成 15 分钟。
- 心跳和任务进度查询设置 30 秒请求超时。
- 每轮结束后等待约 3、12、15 秒依次查询，给服务端最多约 30 秒结算时间（另加请求耗时）。查询失败不能视为进度未增长。
- 确认主播仍在直播且进度未增长时，等待 15 秒，重新发 E 心跳建立新会话，补看一轮。中断前的时长不直接算作服务端已完成进度。
- 补看后仍无增长，保存恢复次数和配置，取消在途请求并禁止新请求，再刷新当前承载脚本的页面，不跳转到目标主播房间。
- 自动刷新按账号和北京时间日期持久化，每个账号每天最多一次，所有房间共享预算。刷新失败也不退还预算。
- 刷新后该房间再尝试一轮；仍无增长就停止当天该房间在此进度上的自动补救。手动刷新或重跑不会清空次数；服务端进度增长或跨天后可重新评估。
- 主播下播时按原配置等待开播；储蓄亲密度达到上限、进度无法查询/解析或发生回退时不自动刷新。

## 刷新与多页面保护

支持 Web Locks 的浏览器使用独占文档锁选择主脚本，不再仅凭 8 秒存活心跳判断其他页面已经退出。旧文档持锁到真正销毁，不在调用刷新前主动解锁。

自动刷新后的页面会等待旧文档释放锁，最多等待 20 秒。若其他页面仍持锁，则当前页面作为 Other，不启动任务；可在控制台查看脚本类型。支持锁但获取失败时不会退回时间戳方式抢占。

不支持 Web Locks 的浏览器保留旧版主脚本判断方式，但禁用自动刷新补救。子 frame 也不自动刷新，以免只刷新 iframe 后不能正确接管顶层页面。面板会显示补救停止。

刷新会结束当前页面全部脚本任务，新页面按保存的配置重新启动，各任务仍按原有服务端进度/完成记录判断是否执行。浏览器节能导致的心跳延迟可能仍然出现；刷新不保证修复网络或服务端计入问题。

## 验证

自动化测试以模拟网络和虚拟时间运行真实观看模块，覆盖第 7 次心跳中断、补看成功、两轮无增长、刷新后成功/失败、持久化限次、延迟结算、查询失败、跨天、下播、亲密度上限以及不具备安全刷新条件的情况。

生命周期测试验证独占锁交接、旧文档不退出时放弃接管、刷新前取消在途请求、拒绝迟到响应和禁止继续发送请求。类型检查及构建用于验证安装产物。

用户连续测试 beta 约三天，未再观察到进度不增长。期间没有触发该异常，因此断网后补看和刷新恢复路径仍主要由模拟测试验证。后续排查时，导出带有“本轮心跳成功累计”“补看一轮”“保存恢复记录并刷新”“当前脚本的类型”的日志，确认刷新前后没有两个 Main 同时发送任务心跳。
